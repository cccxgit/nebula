# 空日志与有内容日志：原始 WAL 缓存组件对照

2026-10-11 在本机完成。这个实验直接调用原始 `AtomicLogBuffer`，比较日志内容大小改变后，缓存保留多少对象。它没有运行 Nebula 服务，也没有模拟 RocksDB，因此不能用来宣称“50 个空间持续写入时 storaged 的 RSS 已实测为某个数值”。通俗解释见上一级 [持续写入与空闲对比](../WRITE-VS-IDLE.md)。

## 已确认的结果

同一个 8MiB 逻辑容量，空日志填满后保留约 28MiB 节点分配；固定 1KiB 内容的日志填满后，本次取样约保留 10.44MiB 的节点加字符串分配。停止有内容的写入、继续追加空日志时，缓存的逻辑字节仍在约 8MiB 附近，实际保留对象却从约 10.44MiB 增至约 28.01MiB。

原因是容量按“16 字节元信息＋内容长度”计算，而节点始终以 64 个记录槽为一组分配。空日志占用的计账字节少，能留下更多条记录，也就留下更多节点。有内容的日志还需要字符串分配，实验将它一起计入，没有只比较节点数量。

| 独立进程中的场景 | 累计追加记录 | 当前计账字节 | 尚未删除的节点 | 节点＋字符串分配字节 |
|---|---:|---:|---:|---:|
| 全为空日志 | 524,288 | 8,388,608 | 8,192 | 29,360,128（28MiB） |
| 全为空日志 | 1,100,000 | 8,388,096 | 8,194 | 29,367,296 |
| 每条内容 256B | 131,072 | 8,373,248 | 482 | 11,598,848 |
| 每条内容 1KiB | 32,768 | 8,386,560 | 128 | 10,944,512（10.4375MiB） |
| 每条内容 1KiB | 131,072 | 8,386,560 | 128 | 10,944,512 |

“尚未删除”包括仍有效和已经标记、暂未物理删除的节点。正常释放每次读者后，原始代码仍可能保留少量脏节点，因为一般要累计超过 5 个才执行这次回收。因此不能把表中的全部节点都称为有效节点。

停写对照来自另一个独立进程，先写 32,768 条 1KiB 内容日志，再连续写入空日志：

| 阶段 | 当前计账字节 | 尚未删除的非空记录 | 尚未删除的节点 | 节点＋字符串分配字节 |
|---|---:|---:|---:|---:|
| 刚结束有内容写入 | 8,386,560 | 8,192 | 128 | 10,944,512 |
| 再追加 32,768 条空日志 | 8,378,368 | 7,808 | 634 | 12,266,496 |
| 再追加 262,144 条空日志 | 8,387,584 | 4,352 | 4,164 | 20,494,336 |
| 再追加 600,000 条空日志 | 8,388,608 | 0 | 8,195 | 29,370,880 |

这验证的是记录组成改变的影响：旧的大记录逐渐退出，新空记录占据更多槽位；并非“没有 GC”。取样中可见淘汰后的记录数量变化和少量脏节点，代码仍按原始方式回收。

## 程序做了什么

- 代码基线：`de9b3ed800a6627d9845e9289b6bbc5b6faf460a` 的 `AtomicLogBuffer.cpp/.h`。运行前用 `git show | cmp` 验证上一级 `baseline/` 与固定提交逐字一致。
- 驱动：[payload-probe.cpp](payload-probe.cpp)。仅在驱动的编译单元开放私有字段读取；没有替换或重写缓存算法。
- 每次调用 `push()` 后，用真实 `iterator()` 读取刚写入的那条，核对 LogID 与完整内容，然后立即析构读者。每次采样都在单线程静止点进行。
- 容量固定 8,388,608B。构造内容为指定长度的 `x` 字符串，它代表缓存层的字节载荷，不是可交给状态机执行的真实业务编码。
- 本机构建 `sizeof(Record)=48`、`sizeof(Node)=3200`。同工程 jemalloc 的节点分配档位为 3584B；256B/1024B 字符串在本机分别占用 320B/1280B 的分配档位。
- 内存统计使用 `malloc_usable_size()` 累计节点及由字符串独立持有的分配；短字符串的内容位于字符串对象内部，避免重复统计。
- 每次采样核对：遍历出的有效节点逻辑字节等于 `size_`；遍历的脏节点数等于 `dirtyNodes_`；读者引用数为 0。全部检查通过。

`node_and_payload_usable_bytes` 是仍由这些缓存对象持有的分配大小，不包含分配器额外元数据、已释放保留页、进程其它对象或内核缓存。CSV 同时保留 `rss_kib`，但不能把二者当成同一个指标。停写进程的 RSS 从 15,736KiB 增至 43,900KiB；其中还含历史分配的保留影响，不据此推算三实例服务的总 RSS。

## 复现与文件

从工程根目录执行：

```bash
bash task/wal-investigation/write-idle-comparison-20261011/run.sh
```

本次已执行并完成。脚本为保护证据会拒绝覆盖已有结果。重复实验时将驱动和脚本放入新的结果目录，并修改脚本中的 `probe_out`，保持原始 `baseline/` 不变。脚本只启动一个 C++ 编译进程，没有运行工程 `make`；工程编译仍遵循最大 `make -j5` 的用户要求。

| 文件 | 内容 |
|---|---|
| [run.sh](run.sh) | 完整编译和四组运行命令、覆盖保护、基线验证 |
| [environment.txt](environment.txt)、[build.log](build.log) | 实际执行时间、编译器、源码 SHA-256、编译输出 |
| [empty.csv](empty.csv)、[empty.meta](empty.meta) | 空日志一直写入，填满后继续写的对照 |
| [payload256.csv](payload256.csv)、[payload256.meta](payload256.meta) | 每条 256B 内容 |
| [payload1024.csv](payload1024.csv)、[payload1024.meta](payload1024.meta) | 每条 1KiB 内容，包含第 8066 条开始淘汰的边界 |
| [after-stop.csv](after-stop.csv)、[after-stop.meta](after-stop.meta) | 先写 1KiB 内容，再改为空日志 |

本实验按记录数推进，没有限速模拟真实心跳，也没有测量生产写入吞吐量。因此不能将一次快速运行的耗时解释为线上填满缓存的时间。它补充了原报告的空闲服务证据，但完整持续写入场景仍需在固定写入速率、载荷和分片分布后单独测量。

# 首期空间级 WAL 参数：开发契约审查

日期：2026-10-11。状态：开发设计建议，产品尚未实现；本轮只读源码，不启动数据库、不修改产品代码。范围：`3.6-memory`，产品基线 `de9b3ed800a6627d9845e9289b6bbc5b6faf460a`；遵循根目录分析规范。本文供需求主文合并，不替代最终评审决议。

## 直接结论

首期设计可以落地，但仅增加“空间 ID 到缓存容量”的映射还不足以发布。需要把配置失效时是否启动、取值何时冻结、配置界面显示什么、空间删除后怎样处理等行为一起固定。建议采用启动快照、非法配置严格拒绝、运行时修改拒绝、对象实际容量可查询这四个原则。只读预检查的集群身份验证还有一个真实接口缺口，不能通过启动 Storage 或发送普通心跳冒充无副作用检查。

## 一、必须在需求主文固定的行为

以下为建议契约，不是当前版本已有行为。

### 1. 开关与空配置

| 输入情况 | 建议行为 | 原因 |
|---|---|---|
| 新开关为 false，映射是 `{}` | 走旧路径，不冻结旧全局变量 | 验证新版本关闭功能时与旧逻辑等价 |
| 新开关为 false，映射非空甚至 JSON 非法 | 不解析、不应用；仅输出一次“映射被忽略”提示，避免打印整个输入 | 开关关闭必须是可操作的应急退路，不能仍被坏映射挡住 |
| 新开关为 true，映射为默认 `{}` | 拒绝启动，指出缺少完整的格式版本、集群和发布身份 | 避免开关已开但实际没有经过身份校验；需要无覆盖时可提供完整文档且 `spaces:{}` |
| 新开关为 true，完整且合法的 `spaces:{}` | 合法；所有业务空间继承冻结默认 | 验证首期启用框架而不改变容量 |
| 非业务 Storage 角色尝试启用 | 明确拒绝该角色启用，而不是静默给 Listener/Meta 套值 | 暴露部署模板用错角色的问题；公共 WAL 类保持兼容 |

离线“检查配置”模式应始终校验映射，不因生产开关为 false 就跳过，输出 `validation_only=true`。这与实际启动时的关闭语义有意不同，帮助提前发现待启用的坏配置。旧二进制不认识新开关，因此关闭开关不等于允许回退旧二进制。

### 2. JSON 格式及精度

建议格式：

```json
{
  "format_version": 1,
  "revision": "cold-trial-01",
  "cluster_id": "12345",
  "spaces": {
    "303": {
      "expected_name": "asset_models",
      "wal_buffer_size": 4194304
    }
  }
}
```

这里的 ID、名称与值都是假设。相较先前方案的示意格式，建议将 `cluster_id` 固定为十进制字符串：真实 ClusterID 是 64 位整数，可能超过一些 JSON 管理工具可精确表达的数值范围，不能让配置系统中途改变集群身份。此格式在实现前应统一，不应兼容多个含糊表达。

建议首期解析约束：

- 顶层与空间项均拒绝未知字段；所有规定字段必填，不接受 `null`。
- `format_version` 只接受整数 `1`；`revision` 为非空可打印发布标识，建议限定 ASCII 字母、数字、点、下划线和短横线，长度不超过 128。
- `cluster_id` 是规范十进制字符串，范围 `1..INT64_MAX`；拒绝符号、前导零及科学计数法。
- `spaces` 的键是规范十进制 GraphSpaceID 字符串，范围 `1..INT32_MAX`；拒绝 `0`、`03` 和 `+3`，防止两个文本键代表同一个 ID。
- `expected_name` 是 Meta 返回的完整空间名，按字节精确比较，不进行大小写或前缀归一化。
- `wal_buffer_size` 是 JSON 整数、单位字节，首期覆盖范围建议 `262144..8388608`。不接受布尔值、浮点、单位字符串；先做 64 位范围检查，再转成底层 `int32_t`。
- 重复 JSON 键必须拒绝，包含顶层和每个嵌套对象；不能只在解析后遍历一个已经去重的 map。需明确选用能报告重复键的解析方式并写测试，现有 `Configuration` 包装没有提供这一保证的契约。
- 建议输入上限 1 MiB、覆盖项上限 10000；这是新功能的保护边界，须由容量评审确认，超过时明确报错而非截断。

范围 `256 KiB..8 MiB` 是首期产品限制，不是“这些值都经过生产安全验证”。若原全局默认高于 8 MiB，未覆盖空间仍保留它，不能因为新功能启用而悄悄改小。启用模式至少拒绝非正全局默认，并检查能以现有 `int32_t` 表达；关闭模式保持旧行为。

### 3. 冻结默认必须有一个明确时间点

推荐在命令行解析完成之后读取新开关、映射和本地 `wal_buffer_size`，形成启动候选；在 Meta 正常就绪、集群与空间验证通过之后，把它发布成不可变快照，之后才创建业务 store。

启用模式下，从 Meta 配置首次加载前就必须安装运行时修改限制，包括 `wal_buffer_size`。否则首次 `waitForMetadReady()` 已可能把本地值改成历史 Meta 值，导致“冻结本地默认”的描述与实际来源不一致。

如现网存在 Meta 管理的 `wal_buffer_size`，上线前应导出其实际值、显式写入本地默认并清理管理冲突。启动收到冲突 Meta 配置时，不应用它，记录拒绝状态；不把这种情况下的默认称为“Meta 当前生效值”。建议预检查把冲突列为阻止启用的检查项；首期不通过改变 `local_config` 一次改变所有现有参数来源。

冻结对象建议至少包括：功能开关、格式版本、实际集群 ID、发布 revision、规范化内容 hash、冻结全局默认、空间覆盖项及身份校验时刻。每个分片只保存其已解析的整数和来源信息，不复制整个 JSON。

### 4. HTTP 和 Meta 的更新语义不同

**HTTP：**两个新参数始终为启动参数；启用模式下的旧 `wal_buffer_size` 同样拒绝运行中修改。建议在执行任何赋值之前先检查整个 HTTP 请求；如果含受保护参数，整个请求返回 HTTP 409，业务错误 `RESTART_REQUIRED`，请求内其他字段也不执行，避免部分成功。即使尝试赋相同值也按启动参数拒绝，语义简单且便于自动化。

**Meta：**新参数禁止注册成可变参数；启用模式下的 `wal_buffer_size` 也禁止被自定义可变清单注册。应用端仍需做二次拦截，以防历史条目或误注册绕过入口。拒绝时不改 gflag，不触发回调，记录参数、来源、拒绝原因、拒绝次数和最近时间。

当前 Meta 配置命令写入 Meta，与 Storage 之后加载配置是异步关系。只改 Storage 时，不能承诺命令发起者同步得到失败。需要把“Meta 已存储”和“Storage 已应用/已拒绝”分开显示；若要给 nGQL 命令同步拒绝，需纳入额外的 Meta 管理入口改造及混合版本设计。

关闭新机制时，旧 `wal_buffer_size` 保留旧更新语义；但旧语义本身也只影响后来构造的缓存，不会自动缩小已存在的对象。诊断接口要能表示同一个进程出现多种实际容量。

## 二、身份校验和预检查不能写成一句“连接 Meta 即可”

### 1. 正式启动校验

当前 Storage 正常心跳会携带或获得集群 ID。校验要读取**成功心跳验证后的 `MetaClientOptions::clusterId_`**，必要时增加只读 getter；不能读取 `Part.cpp` 的 `FLAGS_cluster_id`，也不能误读 `MetaClient` 另一个没有该赋值链的同名成员。

启用时校验所有覆盖项是否在 Meta 完整空间清单中，不能只检查当前机器承载的本地分片。未知 ID、名称不匹配、集群 ID 不匹配统一拒绝创建业务 store；错误要包含 JSON 字段路径、期望身份与实际身份。无本地分片的合法空间覆盖项可以保留，为未来迁移接收方准备。

### 2. 无副作用预检查的接口缺口

不能调用完整 Storage 启动再“检查后退出”。`StorageDaemon` 会先写 pid 文件；`NebulaStore::init()` 会启动 Raft 服务并打开本地存储；普通 `waitForMetadReady()` 会心跳、加载/注册配置、保存版本并启动后台线程。普通心跳还会在 Meta 更新宿主机信息，不是只读验证。

建议把预检查拆开，并写清每一层已经证明什么：

1. **离线检查**：独立入口共享解析器，不写 pid、不 daemonize、不打开 data/WAL 目录、不监听端口、不启动 StorageServer；只检查类型、范围、重复键，输出规范化 hash。
2. **Meta 空间检查**：使用直接只读 RPC 获取完整空间 ID/名称清单和相关现存配置，不走 `waitForMetadReady()`；有超时，检查完退出。这可验证目标空间，但现有 `listCluster` 响应不包含集群 ID。
3. **正式启动身份门禁**：必须在业务 store 构造前完成正常心跳身份校验，即使预检查先前通过也重新校验。

若首期要求“预检查必须权威确认连接的 Meta 集群身份且完全只读”，应增加一个只读 Meta 身份查询或等效已验证接口，并明确纳入首期改动范围。若不扩展 Meta，预检查结果必须明确标为 `cluster_identity_verified=false`，不能以“全部检查通过”替代正式启动门禁。通过可信运维导出或已运行 Storage 的诊断结果辅助核对，只能作为有来源的辅助证据，不等价于确认本次 Meta RPC 连接身份。

建议责任人评审这一取舍；它关系首期是否仍能承诺“只改 Storage、Meta 无须升级”。不要以注册一个虚假 Storage 或把角色设为 UNKNOWN 后发普通心跳来规避，因为服务端心跳仍有宿主机写入路径。

## 三、空间生命周期和并发边界

| 场景 | 要求的行为 |
|---|---|
| 启动时覆盖 ID 不存在 | 严格拒绝；需清理发布文件，不以默认值兜底 |
| 覆盖 ID 存在，但本机无分片 | 校验通过；显示为已验证但尚未实例化 |
| 正常运行后删除被覆盖空间 | 沿用已有 DROP 流程释放对象；冻结映射可以留着，不能阻止合法删除 |
| 删除后同名重建 | 新 ID 不自动继承旧覆盖；新空间采用冻结默认 |
| 之后重启，发布文件仍保留被删 ID | 严格拒绝；运维需先从策略删除旧 ID |
| 运行中新建未覆盖空间 | 继承启动默认；不读后来被改的原始 JSON/gflag |
| 分片迁入、新 Learner、本地盘恢复 | 统一经过业务 `newPart` 的已解析策略选择；不能只覆盖首次集群启动路径 |
| Leader/Follower 切换 | 对象容量不变；不按角色重新取容量 |
| 完成验证后 Meta 正好删除空间 | 不为“保持覆盖”重新创建空间或绕过已有成员检查；按已有移除流程结束对象 |
| 元数据恢复或切换目标集群 | 重新校验集群 ID 和空间映射；不把历史配置未经审核直接套用 |

这里的存在性校验是“启动验证时刻的快照”，并不是和之后所有 DDL 之间的分布式事务。首期配置发布期间建议暂停目标空间 DROP/重建；内核仍需测试竞态安全，不能靠运维约束避免悬空指针。验证完成后不在每次读写访问 Meta，处理新对象时也不临时改全局变量。

策略对象建议由 store 持有 `shared_ptr<const ...>`，分片构造时复制其小型解析结果。诊断采样短暂持有 store 的读锁取得 `shared_ptr<Part>` 快照，再释放锁读取不可变容量并组装响应，避免一边 DROP 一边使用裸指针，也避免持锁序列化大型 JSON。

## 四、实际生效诊断的最小契约

建议新增只读入口 `GET /space_kernel_options`；这是设计名称，当前二进制不存在。首期接口应能表达“没有对象”“混合容量”和“已拒绝更新”，不能只展示输入 JSON。

| 层级 | 必需字段及语义 |
|---|---|
| 进程 | `schema_version`、实例标识、二进制版本、启动时间、角色、enabled、`cluster_id` 十进制字符串、revision、policy_hash、冻结默认或 legacy 模式、采样时间 |
| 配置项 | space_id、expected_name、启动验证名称/时间、来源 `space_override` 或 `startup_default`；配置项数量与本地已实例化数量分开 |
| 生效项 | space_id、角色、本地副本数、`capacity_distribution`，每档给 capacity_bytes 和 part_count；来自实际对象容量 |
| 无对象覆盖项 | local_part_count=0，状态 `VALIDATED_NO_LOCAL_PART`；actual capacity 为空，不能伪装成已应用成功 |
| 更新拒绝 | 参数、来源 HTTP/Meta、reason、count、last_time；日志不要无限频率打印 |
| 运行采样边界 | 明确采样为本实例近时快照，不保证与集群 DDL、其他实例同一时刻一致 |

可提供按 space_id 过滤和分页，限定响应规模；参数非法返回 400，正常查询空本地对象可返回 200 加上述状态。读者正常读取诊断不应改变缓存的引用计数或触发 WAL 全量遍历。

建议 hash 计算包含格式版本、集群身份、启用语义、冻结全局默认和按数值 ID 排序的空间语义内容；不包含 revision、空白和字段输入顺序。revision 是发布标签，hash 是内容标识；两者都检查。同一 JSON 配上不同全局默认，应产生不同的有效策略 hash。

空间配置容量不是实际 RAM 字节，诊断不能给字段命名 `memory_limit`。若增加 WAL 节点/计账字节观测，需与配置容量、RSS、容器内存分别命名；实时内存计数准确性需独立设计，不能把已有实验用统计补丁直接当成已发布生产接口。

## 六、开发验收必须包含的反例

1. 开关关闭但 JSON 损坏：服务走旧路径；检查模式明确失败。否则回退开关不是可靠退路。
2. 两个嵌套同名键、`03`/`3`、浮点容量、超大 64 位数：明确拒绝，不截断、不覆盖前值。
3. 全局默认不同但空间 JSON 相同：未覆盖空间容量不同，策略 hash 也不同。
4. 历史 Meta 配置和自定义 MUTABLE 含保护键：原变量与实际对象不变，拒绝状态可见。
5. HTTP 同一请求含合法动态键与保护键：整个请求无写入，返回 `RESTART_REQUIRED`。
6. 未在本机承载的合法覆盖：预检查通过并显示未实例化；随后迁入时容量正确。
7. 删除后同名重建：新 ID 用默认；旧覆盖在下一次启动必须被拒绝；运行中删除不使进程崩溃。
8. 诊断请求与移除分片并发：无裸指针悬挂，容量分布总数对应采样快照；不要求跨实例原子快照。
9. 预检查运行期间监测：无 pid/data/WAL 写入、无监听端口、无新增主机心跳和版本注册；受控输出日志除外。
10. 旧版本回退：移除新 flags 后才启动旧二进制；回退 8 MiB 的内存余量已计算，不只验证能解析配置。

## 七、责任人评审项与建议决策

| 事项 | 建议 | 需要确认的原因 |
|---|---|---|
| 完全只读预检查是否必须权威校验 Meta cluster ID | 若必须，纳入只读 Meta 身份接口；否则明确输出未验证，依赖正式启动门禁 | 影响首期 Meta 升级范围与发布顺序 |
| 输入规模 | 1 MiB / 10000 覆盖项作为首期上限 | 需结合现网及未来空间量，避免拍脑袋变永久产品限制 |
| 覆盖容量范围 | 256 KiB..8 MiB，首轮试 4 MiB | 范围属于产品决定，安全候选仍由压测决定 |
| 非业务角色配置启用 | 启动拒绝 | 暴露误配置的收益与统一模板兼容需求需确认 |
| HTTP 混合请求 | 含保护键时整单拒绝，其他老请求不改语义 | 避免新参数造成部分成功困惑 |
| 启用模式历史 Meta 配置冲突 | 预检查阻断发布；应用端保持本地快照并拒绝更新 | 运维必须先迁移原有效值，防默认来源误解 |

这些评审不妨碍编写解析器、类型化传参和测试，但最终配置契约冻结前不应发布生产。现阶段最可靠的改造仍是“启动生成不可变策略 → 业务 Part 构造时选值 → 实际对象诊断”；首期不混入在线缩容、自动冷热判定或全资源按空间配额。

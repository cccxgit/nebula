# 传统手写查询方式 vs 智能系统方式 专家追问应答版

## 问题 1：手写 nGQL 明明也能做，为什么还需要智能系统？

回答：

手写 nGQL 确实能做，但它要求使用者同时具备三类能力：

- 业务理解能力
- 图模型理解能力
- nGQL 编写能力

智能系统的价值，不是替代数据库，而是把这三层之间的转化成本降下来，让非图数据库专家也能高效使用图能力。

## 问题 2：是不是只是给数据库套了一层自然语言外壳？

回答：

不是。它至少做了三件事：

1. 通过 Skill 约束模型行为，避免误用图数据库
2. 通过 MCP 标准化 NebulaGraph 工具能力
3. 通过路径、邻居、schema 探索等图原语封装，降低图查询门槛

所以它不是简单 UI，而是一个智能交互中间层。

## 问题 3：对专家用户是不是价值不大？

回答：

对专家用户，手写 nGQL 当然仍然重要，尤其在复杂调优和底层排障时更直接。

但这套系统的价值重点不在替代专家，而在放大图数据库能力的适用人群。也就是说，它更重要的目标是让更多内部用户能够用上图数据，而不是只让专家更快写一条查询。

## 问题 4：为什么说这种方式更有商业价值？

回答：

因为企业真正有价值的问题，通常不是“怎么写一条图查询”，而是：

- 哪些商户值得推荐
- 哪些区域适合选址
- 哪些实体互为竞品
- 哪些评论反映风险

智能系统可以让用户直接提这些业务问题，再自动映射到图分析能力上。这比要求业务方自己写 nGQL，更容易放大商业价值。

## 问题 5：这种方式最大的技术优势是什么？

回答：

最大的技术优势有两个：

1. 降低图数据库使用门槛
2. 保留图数据库原生能力

也就是说，它不是把图数据库降级成文本搜索，而是在保留路径、邻居、多跳关系这些图能力的前提下，提高交互友好性。

## 问题 6：它最大的边界是什么？

回答：

边界在于：

- 底层 schema 仍然决定上限
- 查询安全和治理仍要加强
- 对复杂业务语义还需要进一步做领域增强

所以它适合作为智能图交互层，而不是完全替代图数据库建模和治理本身。

## 问题 7：一句话总结它相对传统手写查询方式的优势

回答：

它最大的优势是把“业务问题”和“图数据库实现细节”解耦了。

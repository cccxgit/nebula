# NebulaGraph 智能交互方案 PPT 逐页正文

## 第 1 页：封面

标题：

NebulaGraph 智能交互方案技术验证与商业价值分析

副标题：

基于 Codex + MCP + NebulaGraph 的图数据库智能交互实践

汇报要点：

- 完成系统验证
- 完成源码级技术分析
- 完成高价值数据集与商业场景设计

## 第 2 页：项目背景

正文：

图数据库在知识图谱、关系分析、风控、推荐、运维依赖分析等场景中具有很高价值，但在实际使用中通常存在三个问题：

1. 图数据库使用门槛高
2. nGQL 需要专门学习
3. 非图数据库专家很难高效使用图数据

因此，我们希望验证一套能够让用户通过自然语言访问 NebulaGraph 的智能交互方案，降低图数据使用门槛，提升图数据库在内部项目中的可用性和业务价值。

## 第 3 页：项目目标

正文：

本项目目标包括三部分：

1. 基于本机 NebulaGraph、开源 Skill、开源 MCP Server 完成系统验证
2. 从源码层面分析系统架构、实现原理和技术竞争力
3. 结合高价值真实业务数据方向，设计能够体现 AI 商业价值的测试场景

本次采用的核心组件包括：

- `NebulaGraph-Skill`
- `nebulagraph-mcp-server`
- `Codex`
- `NebulaGraph`

## 第 4 页：总体方案

正文：

整体方案采用分层架构，核心链路如下：

- 用户通过自然语言提出问题
- Codex 通过 `NebulaGraph-Skill` 理解任务并选择工具
- `nebulagraph-mcp-server` 通过 MCP 协议向 Agent 暴露图数据库能力
- NebulaGraph 执行真实图查询、路径分析和邻居探索

从架构角度看，这是一套 `Agent + Skill + MCP + Graph DB` 的组合方案，不是单纯的数据库脚本封装。

## 第 5 页：架构价值

正文：

这套架构的价值在于职责拆分非常清楚：

- Skill 负责领域行为约束
- MCP 负责协议标准化
- NebulaGraph 负责图计算与图存储
- Agent 负责自然语言理解与结果表达

这使系统既保留了大模型的自然语言交互优势，又避免了大模型直接承担全部数据库控制逻辑，从而提升系统稳定性和可治理性。

## 第 6 页：NebulaGraph-Skill 的作用

正文：

`NebulaGraph-Skill` 的核心作用不是提供静态文档，而是把通用大模型约束成图数据库专家代理。

它做了四件关键事情：

1. 定义图数据库相关触发条件
2. 将请求分类为 Exploration、Query、Mutation、Schema Design
3. 规定不同请求应优先使用哪些工具
4. 固化 NebulaGraph 的常见易错点

因此，Skill 实际上相当于一个图数据库领域的运行时行为编排器。

## 第 7 页：Skill 的技术优势

正文：

`NebulaGraph-Skill` 有三个关键优势：

1. 任务分类驱动工具选择
   - 模型不是盲目选工具，而是按场景走固定工作流
2. 三层渐进式知识加载
   - 先加载高频规则，再按需加载参考资料，最后才查官方文档
3. 易错点前置约束
   - 如 `==` 与 `=` 区别、属性访问格式、索引依赖、schema 变更同步延迟等

这些设计共同提升了模型在图数据库场景中的回答质量和工具调用正确率。

## 第 8 页：MCP Server 的作用

正文：

`nebulagraph-mcp-server` 的作用，是把 NebulaGraph 的能力包装成标准 MCP 工具，让 Agent 可以以统一协议调用图数据库。

它当前暴露的核心能力包括：

- `list_spaces`
- `get_space_schema`
- `execute_query`
- `find_path`
- `find_neighbors`

从定位上看，它是一个图数据库能力协议适配层，而不是业务逻辑层。

## 第 9 页：MCP Server 的技术优势

正文：

`nebulagraph-mcp-server` 的技术优势体现在三个方面：

1. 协议标准化
   - 通过 MCP 解耦数据库与具体 Agent 平台
2. 图原语工具化
   - 把路径查询、邻居探索等图能力直接做成高频工具
3. 通用与专用并存
   - 同时保留 `execute_query` 的通用查询能力和专用图工具能力

这种设计兼顾了灵活性与可复用性。

## 第 12 页：为什么它适合图数据库场景

正文：

图数据库与关系数据库最大的不同，不在于“多一个数据库产品”，而在于交互模式完全不同。

图数据库高价值场景通常围绕：

- 多跳遍历
- 邻居探索
- 路径发现
- 实体关系解释
- 图模型设计

这套方案对这些图场景做了显式支持，因此比通用数据库 Agent 更适合图谱应用。

## 第 13 页：技术竞争力总结

正文：

从技术竞争力看，这套方案有三类优势：

1. 领域适配力
   - 针对 NebulaGraph 和 nGQL 做了专门设计
2. 协议兼容力
   - 基于 MCP，可接入多种 Agent
3. 工程复用力
   - Skill 与 MCP 解耦，便于独立升级

因此它适合作为内部图数据库 Copilot 或智能图谱交互基座。

## 第 14 页：任务三数据集选择

正文：

为了说明项目的 AI 商业价值，本次选择的公开数据方向是：

- `Yelp Open Dataset`

选择原因包括：

- 这是典型的本地生活商业图谱
- 数据实体和关系结构丰富
- 非常适合推荐、竞对、选址、评论分析等商业场景
- 比纯学术数据更容易向专家说明业务落地价值

## 第 15 页：数据集商业价值

正文：

基于 Yelp 官方公开信息，该数据方向包含：

- 商户
- 用户
- 评论
- 品类
- 城市和区域

这类数据天然适合建图，并可直接回答：

- 哪些商户值得推荐
- 哪些商户互为竞品
- 哪些区域存在供需错配
- 哪些评论反映了经营风险

这使其成为非常适合凸显图数据库 AI 价值的数据方向。

## 第 16 页：高价值业务测试场景

正文：

基于该数据方向，我们设计了五类重点测试场景：

1. AI 本地生活推荐
2. 相似商户与替代推荐
3. 选址与市场空白分析
4. 评论根因与经营问题诊断
5. 风险与机会识别

这些场景都明显强于“简单查库”，更能体现图数据库和 AI 结合后的商业价值。

## 第 17 页：商业价值体现

正文：

任务三设计的价值不在于让系统回答一个固定问题，而在于展示：

- AI 可以理解业务问题
- AI 可以自动调用图工具
- AI 可以把图查询结果解释成经营建议

这意味着图数据库不再只是底层存储，而是可以成为前台智能分析能力的一部分。

## 第 18 页：当前不足

正文：

尽管方向正确、验证成功，但当前方案还存在以下不足：

1. `execute_query` 治理能力不足
2. 查询参数存在字符串拼接风险
3. 输出以文本为主，结构化不足
4. 缺少权限、审计、可观测性等生产能力

因此当前更适合：

- PoC
- 内部试用
- 能力基座验证

## 第 19 页：落地建议

正文：

建议采用分阶段推进方式：

第一阶段：

- 作为内部图数据库助手试点使用

第二阶段：

- 增强安全、权限、审计、结构化输出

第三阶段：

- 接入内部业务平台和图谱平台

这种路径投入可控，也最符合当前系统成熟度。

正文：

本次验证结果可以得出以下结论：

1. 技术路线正确
2. 系统验证成功
3. 对图数据库场景有明确针对性优势
4. 具备内部项目继续工程化推进的价值

将其作为内部智能图谱交互能力基座继续建设，优先补齐治理能力，再围绕高价值业务场景做试点落地。

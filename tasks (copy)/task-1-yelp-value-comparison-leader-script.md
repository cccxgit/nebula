# 传统手写查询方式 vs 智能系统方式 领导口播版

## 第 1 页口播

这页主要想说明一个核心差异。

传统图数据库使用方式，本质上还是专家工具模式。用户如果想查一个问题，前提是先要懂图模型、懂 tag 和 edge、懂属性路径，还要会写 nGQL。也就是说，业务问题要先被翻译成图查询语言，才能进入系统。

但智能系统方式不一样。用户只需要直接提业务问题，比如“帮我找 Cleveland 评分高、评论多的餐馆”，或者“这个用户和这家店是什么关系”。系统会自动理解意图、识别 schema、选择工具，再把结果组织成业务上能看懂的答案。

所以两者最大的区别不是数据库有没有变快，而是使用门槛有没有降下来。

一句话总结，传统方式是“人适应数据库”，智能系统方式是“数据库能力适应人”。

这件事的意义在于，它可以把图数据库从少数专家才能使用的能力，变成更多研发、运营、分析甚至业务人员都能直接消费的能力。

## 第 2 页口播

这页我们用两个很直观的例子说明。

第一个例子是“找 Cleveland 评分高、评论多的餐馆”。

如果用自然语言，这就是一句很普通的业务问题。但如果用传统方式手写 nGQL，背后其实要知道很多细节：城市怎么建模、餐馆怎么建模、评论数在哪个属性上、NebulaGraph 的排序和返回规则怎么写。也就是说，用户真正想问的是业务问题，但系统要求他先变成一个图数据库工程师。

第二个例子是“这个用户和这家店是什么关系”。

自然语言表达很简单，但手写查询时，开发者得先判断是用路径查询、还是用 MATCH，还要决定搜索方向、深度、是否保留属性。这个过程本身就把很多非专家挡在门外了。

所以我们这套智能系统的真正价值，不只是帮用户少写几条查询语句，而是缩短了“业务问题”到“图分析结果”之间的距离。

从企业内部推广角度看，这一点非常关键。因为真正决定一个能力能不能用起来的，很多时候不是底层数据库强不强，而是有没有办法让更多人低门槛用起来。

最后一句建议可以这么说：

对于图数据库专家，手写 nGQL 当然仍然有价值；但对于更广泛的内部用户，智能系统方式更有推广价值，也更有机会放大图数据资产的实际业务收益。

# NebulaGraph 智能交互方案汇报讲稿

## 第 1 页：项目背景

我们这次工作的目标，是验证一套基于 NebulaGraph 的智能交互方案，解决图数据库使用门槛高、nGQL 专业性强、业务人员难以直接使用的问题。

传统模式下，只有懂图数据库和懂 nGQL 的工程师能高效使用图数据。我们希望把这件事变成：用户通过自然语言提出问题，系统自动完成图空间理解、schema 理解、路径分析和图查询执行。

## 第 2 页：总体方案

整体方案由三部分组成：

1. `NebulaGraph-Skill`
2. `nebulagraph-mcp-server`
3. `NebulaGraph`

其中：

- Skill 负责把通用大模型约束成图数据库专家代理
- MCP Server 负责把图数据库能力标准化成可调用工具
- NebulaGraph 负责真实执行图查询与图遍历

所以它不是一个简单脚本，而是一套 `Agent + Protocol + Graph DB` 的分层架构。

## 第 3 页：这套方案为什么成立

核心原因是职责拆分清楚：

- 用户意图理解，交给 Agent
- 领域行为约束，交给 Skill
- 工具协议适配，交给 MCP
- 图计算执行，交给 NebulaGraph

这样的好处是：

- 模型不需要直接处理所有数据库细节
- 数据库也不需要感知上层大模型
- 二者之间通过 MCP 做标准连接

## 第 4 页：Skill 的价值

Skill 最大的价值，不是“提供文档”，而是“规定模型该怎么工作”。

它做了四件事：

1. 定义触发条件
2. 定义任务分类
3. 定义工具选择路径
4. 固化 NebulaGraph 的高频易错点

所以 Skill 实际上相当于一个图数据库领域的行为编排层。

## 第 5 页：MCP Server 的价值

MCP Server 的价值在于把 NebulaGraph 能力标准化了。

它提供的核心工具包括：

- `list_spaces`
- `get_space_schema`
- `execute_query`
- `find_path`
- `find_neighbors`

其中前两个负责理解环境，中间一个负责通用执行，后两个负责图数据库最有价值的原生能力，也就是路径和邻居探索。

## 第 6 页：为什么它有图数据库特色

普通数据库 Agent 更多偏向“表查询”。

而图数据库真正高价值的交互是：

- 点和边的结构理解
- 多跳遍历
- 邻居探索
- 路径发现
- 图建模辅助

这套方案对这些场景都做了显式支持，因此它不是一个泛化数据库工具，而是一个面向图数据库的专用智能交互层。

## 第 9 页：技术竞争力

我认为这套方案的竞争力主要有三点：

1. 对图数据库场景有原生适配
2. 用 MCP 实现了模型与数据库的解耦
3. 用 Skill 提升了模型使用图数据库的正确率

换句话说，它不仅能用，而且具备继续工程化演进的价值。

## 第 10 页：任务三数据集选择

为了证明商业价值，我们选择的公开数据集方向是 `Yelp Open Dataset`。

原因是它不是纯学术图，而是本地生活商户、用户、评论和品类关系构成的真实业务图谱，非常适合展示：

- 本地搜索与推荐
- 商户洞察
- 竞对分析
- 选址分析
- 风险识别

这个数据方向更能体现 AI 商业化落地价值。

## 第 11 页：为什么这个数据集有价值

根据 Yelp 官方开发者页面，Yelp Open Dataset 提供 businesses、reviews、user data 的子集。

根据 Yelp 官方工程文章，这个开放数据集包含：

- 约 500 万 reviews
- 超过 110 万 users
- 超过 15 万 businesses
- 覆盖 12 个 metropolitan areas

这说明它既真实、又关系丰富，非常适合建图。

## 第 12 页：商业场景示例

基于这个数据集，我们可以设计非常有价值的测试场景：

1. 自然语言本地生活推荐助手
2. 商圈与城市选址分析助手
3. 商户竞对与口碑差距分析
4. 负面评论根因发现
5. 多门店经营机会识别
6. 银行/保险/平台侧的风险与机会洞察

这些都比单纯查路径更能体现商业价值。

## 第 13 页：当前边界

这套方案现在已经适合：

- PoC
- 内部研发助手
- 图谱分析辅助工具

但还不建议直接作为生产核心服务上线。原因是还需要补齐：

- 权限控制
- 风险语句限制
- 审计日志
- 结构化结果输出
- 可观测性

## 第 14 页：建议落地路径

建议分三阶段推进：

1. 内部试用
2. 工程治理增强
3. 平台化接入和业务化推广

这条路径投入相对可控，收益也更容易量化。

## 第 15 页：结论

最后的结论是：

- 这套方案技术方向正确
- 系统验证已经成功
- 对图数据库场景有明显针对性优势
- 具备内部项目落地和继续工程化建设的价值

如果继续投入，建议优先围绕“安全治理、结构化输出、业务语义增强”三个方向推进。

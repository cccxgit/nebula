# NebulaGraph 智能交互方案答辩问答

## 1. 为什么不直接让大模型生成 nGQL，然后应用自己执行？

因为这样会把三类问题混在一起：

- 任务理解
- 查询语法生成
- 数据库执行约束

当前方案通过 `Skill + MCP` 把这三层拆开，稳定性和可治理性更高。

## 2. Skill 的核心作用是什么？

Skill 的核心作用不是提供文档，而是约束 Agent 的行为：

- 什么时候调用什么工具
- 什么情况下先看 schema
- NebulaGraph 的易错点有哪些
- 什么时候应该退化到通用查询

它本质上是领域行为编排层。

## 3. 为什么要用 MCP？

MCP 的价值在于标准化工具接口。

这样可以把 NebulaGraph 能力独立出来，不绑定某一个模型或某一个 Agent 产品。未来无论接 Codex、Claude、LlamaIndex 还是其他支持 MCP 的平台，都能复用这层能力。

## 4. 这套方案的核心竞争力是什么？

核心竞争力有三点：

1. 面向图数据库场景做了原生适配
2. 将路径、邻居等图原语工具化
3. 用 Skill 降低大模型误用图数据库的概率

## 5. 为什么说它比普通数据库 Agent 更适合图场景？

因为图数据库的关键交互不是简单表查询，而是：

- 路径
- 多跳遍历
- 邻居探索
- schema 理解

这套方案对这些高频图模式做了专门设计。

## 6. 现在能直接上生产吗？

不建议直接作为生产核心服务上线。

当前更适合作为：

- PoC
- 内部工具
- 图数据库 Copilot 基座

生产化前要补：

- 权限控制
- 风险语句限制
- 审计日志
- 结构化输出
- 可观测性

## 7. 当前最大的风险点是什么？

最大的风险点有三个：

1. `execute_query` 可以执行任意 nGQL
2. 查询参数通过字符串拼接构造
3. 输出结果主要是文本，不利于二次系统处理

## 8. 为什么这套方案值得继续投入？

因为它验证了一个非常关键的方向：

图数据库可以通过标准协议和领域化 Skill 被大模型稳定调用。

这意味着后续可以持续沉淀成内部智能图谱平台的共性能力。

## 9. 后续最优先要做什么？

优先级建议如下：

1. 读写分级与安全治理
2. 结构化返回与前端可视化支持
3. 结合内部业务语义做领域增强

## 10. 一句话向专家总结这套方案

这是一个以 MCP 为协议中枢、以 Skill 为领域约束、以 NebulaGraph 为执行底座的智能图数据库交互框架，方向正确，验证成功，具备内部工程化演进价值。

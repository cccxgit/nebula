# 传统手写查询方式 vs 智能系统方式 3 分钟正式汇报版

本部分我想重点汇报一下，为什么我们认为这套智能系统相比传统手写查询方式有明显价值。

先说传统方式。传统图数据库使用方式，本质上还是一种专家使用模式。用户如果想查询一个问题，不仅要理解业务本身，还必须先理解图数据库的底层建模方式，比如哪些是顶点、哪些是边、属性挂在哪个实体上，以及查询时到底该用 `MATCH`、`GO` 还是 `FIND PATH`。换句话说，业务问题必须先被翻译成图数据库语言，才能进入系统。

但实际工作里，大多数业务人员、运营人员、分析人员并不会使用 nGQL，也不应该要求他们先变成图数据库工程师，才能使用图数据能力。这也是图数据库在很多企业内部“能力很强，但真正用起来的人不多”的一个重要原因。

我们这次验证的智能系统，核心价值就在于改变这个问题。它不是替代数据库，也不是替代图查询本身，而是在用户和图数据库之间增加了一层智能交互能力。用户可以直接提业务问题，比如“帮我找 Cleveland 评分高、评论多的餐馆”，系统会自动去理解这个问题背后的图关系，自动识别需要用到的图空间、schema 和查询路径，再调用对应工具或者生成查询，把结果组织成用户能直接看懂的业务答案。

我们在 Yelp 图数据上做了一个非常直观的对比。比如同样是找 Cleveland 评分高、评论多的餐馆，自然语言只是一句业务问题。但如果手写 nGQL，开发者必须明确知道城市和餐馆在图里是怎么建模的，必须知道城市不是普通字段，而是通过 `LOCATED_IN` 连到 `city` 顶点，必须知道餐馆是通过 `HAS_CATEGORY` 关联到 `Restaurants` 类别，还要处理 NebulaGraph 自己的排序和返回语法细节。这说明，传统方式关注的是技术实现细节，而智能系统关注的是业务意图表达。

第二个例子是“这个用户和这家店是什么关系”。自然语言里，这是一个非常简单的关系解释问题。但如果手写查询，开发者要自己判断是不是用路径查询，要不要双向搜索，最多搜几跳，是否保留路径属性。对图数据库专家来说这不是问题，但对大多数内部用户来说，这个门槛是很高的。智能系统则可以把这种抽象问题直接映射成路径分析动作，并把返回结果解释成业务关系链。

所以我认为，这套系统最重要的价值，并不是让数据库执行更快，而是显著缩短了“业务问题”到“图分析结果”之间的距离。它降低了图数据库使用门槛，降低了 schema 和记忆成本，提升了探索效率，也让图数据库能力具备了更强的内部推广可能性。

最后一句结论可以概括为：传统方式是“人去适应数据库”，而智能系统方式是“让数据库能力更自然地适应人”。对于专家用户，手写 nGQL 依然必要；但对于更广泛的研发、运营、分析和业务团队，智能系统方式更有推广价值，也更有机会把图数据真正转化成业务价值。

# Nebula Graph Balance Bug 修复测试计划

问题：
Nebula Graph 在 storage 服务水平扩容后，执行数据均衡不稳定，经常失败。

用途：
- 记录复现步骤
- 记录修复前的失败表现
- 记录修复后的验证方案
- 形成回归测试清单
- 为 PR 和发布提供验证依据

---

## 1. 测试目标

### 主目标
验证修复后，在 storage 服务水平扩容场景下，data balance / storage balance 能够稳定执行，不再经常失败。

### 次目标
验证修复不会引入以下副作用：
- 非扩容场景的 balance 被破坏
- 原有正常迁移路径被破坏
- 重试逻辑、状态机、幂等逻辑出现退化
- 新增日志或保护逻辑影响正常性能或可读性

## 3. 修复前复现步骤

### 标准复现步骤
1. 启动基础集群
2. 导入测试数据
3. 确认集群稳定
4. 执行 storage 水平扩容
5. 等待节点注册、心跳和基础状态稳定
6. 执行 data balance / storage balance
7. 观察任务执行过程与日志
8. 记录失败现象、失败时间点、失败日志和最终状态

### 需要记录的内容
- balance 发起时间
- 失败时间

- 失败前最后一个正常状态
- 失败后 cluster/part 状态
- 是否可重试
- 重试后行为是否变化

## 5. 修复后验证步骤

### 基础验证
1. 使用与修复前相同的复现环境
2. 重新执行扩容流程
3. 再次执行 balance
4. 观察是否仍出现相同失败
5. 检查日志中的关键状态流转是否合理
6. 检查最终数据分布、task/job 状态是否一致

### 预期结果
- [ ] balance 可以稳定完成
- [ ] 不再出现修复前高频失败日志
- [ ] task/job 状态流转合理
- [ ] 最终数据分布符合预期
- [ ] 重试逻辑未出现异常
- [ ] 没有新增明显异常日志

## 6. 回归测试场景

### R1. 不扩容时执行 balance
目的：
验证修复不会破坏原有正常场景

检查项：
- [ ] 正常执行
- [ ] 无新增异常
- [ ] 状态流转正常

---

### R2. 扩容后执行一次 balance
目的：
验证主修复场景

检查项：
- [ ] 成功完成
- [ ] 无高频失败
- [ ] 日志与状态一致

---

### R3. 扩容后重复执行 balance
目的：
验证幂等性和重复执行稳定性

检查项：
- [ ] 重复执行不出现异常失败
- [ ] 不会因已完成状态导致误判
- [ ] 不会出现脏状态积累

---

### R4. 扩容后人工制造轻微抖动/延迟
目的：
验证修复对时序抖动是否更稳健

检查项：
- [ ] 不因轻微波动立即失败
- [ ] 重试策略合理
- [ ] 日志可解释

---

### R5. 失败后重试
目的：
验证失败恢复与幂等性

检查项：
- [ ] 失败后再次执行不会立即进入异常状态
- [ ] 清理/恢复逻辑正确
- [ ] 不会出现重复任务或状态冲突

---

### R6. leader 变化相关场景
目的：
验证与 leader 切换耦合是否被放大

检查项：
- [ ] leader 变化时不会异常放大失败
- [ ] 日志和状态判断合理

---

## 7. 关键观察指标

建议重点观察：

### 功能结果
- balance 是否成功完成
- 最终 partition 分布是否符合预期
- job/task 最终状态是否一致

### 稳定性
- 连续执行多轮是否稳定
- 是否仍然存在随机失败
- 失败是否可解释、可恢复

### 状态机
- 是否存在跳变
- 是否存在重复成功/失败写入
- 是否存在任务卡住

### 日志可观测性
- 是否能从日志恢复时间线
- 是否能定位失败前最后一个正常状态
- 是否能区分真实失败和误判失败

### 日志与诊断测试

- 失败路径是否有足够诊断信息

# Nebula Graph 复杂 Bug 修复的 Vibe Coding 上手手册

适用场景：
- 你只能使用网页版 Codex
- 你通过 GitHub 仓库 + Codex 问答来推进工程问题
- 你正在处理一个复杂、可复现、可定位日志与代码的线上/准线上 bug
- 当前具体问题：**Nebula Graph 在 storage 服务水平扩容后，执行数据均衡不稳定，经常失败，需要修复**

---

## 0. 先明确：这不是“让 AI 直接修 bug”，而是“借 bug 学会工程化 Vibe Coding”

对初学者来说，最容易失败的方式是：
- 一上来就让 Codex “直接修好”
- 没有先建立问题边界
- 没有让 Codex 先解释仓库、模块、调用链、状态机、日志链路
- 没有固定提示词与验收格式

你应该采用下面这条主线：

**先 Ask 建图谱 → 再 Ask 做分析 → 再 Code 做最小修复 → 再 Ask 审查 → 再 Code 迭代 → 最后沉淀为 AGENTS.md / Skill / 维护文档**

---

## 1. 这个 Nebula Graph bug，为什么特别适合拿来练 Vibe Coding

这个问题具备很好的训练价值，因为它同时包含：
- **复杂分布式系统背景**：storage 水平扩容、数据均衡、任务执行状态、失败重试、节点拓扑变化
- **可复现环境**：适合让 Codex围绕“复现-定位-验证”闭环工作
- **日志与代码可定位**：适合训练“从日志回溯到状态机/模块/函数”的能力
- **修复不是纯算法题**：往往涉及并发、状态同步、时序、重试、异常处理、幂等、元数据一致性

这类 bug 特别适合用来练以下能力：
1. 读大仓库
2. 画调用链
3. 从日志定位代码路径
4. 从现象归纳根因假设
5. 做最小修复
6. 设计回归测试
7. 长期维护修复节奏

---

## 2. 你应该怎样用这个 bug 来上手 Vibe Coding

### 阶段 A：先建立“问题地图”，不要急着改代码

你的第一个目标不是修复，而是让 Codex 帮你建立一张“问题地图”。

你需要先搞清楚：
- 数据均衡功能的总体链路是什么
- storage 扩容后，哪几个模块参与了 balance
- 调度入口、任务状态、执行器、失败处理、重试逻辑分别在哪
- 元数据和 storage 实际状态在哪里汇合
- 日志从哪里打印、哪些关键日志最能对应代码状态

#### 提示词 1：读仓库与问题域

```text
请先不要修改代码。

我在排查一个复杂工程 bug：
Nebula Graph 在 storage 服务水平扩容后，执行数据均衡不稳定，经常失败。

请先做这几件事：
1. 用初学者能懂的话解释这个仓库里与 data balance / storage balance 最相关的模块
2. 找出相关入口、核心执行链路、任务状态流转位置
3. 列出最值得先读的 10 个文件，并按重要性排序
4. 告诉我阅读顺序
5. 说明哪些地方最可能与“扩容后执行失败”有关
```

#### 提示词 2：根因假设树

```text
请先不要修改代码。

问题背景：
Nebula Graph 在 storage 服务水平扩容后，执行数据均衡不稳定，经常失败。
当前有可复现环境，也可以提供日志和代码定位信息。

请基于代码结构和这个现象，输出一棵“根因假设树”：
1. 最可能的 5 到 8 类根因
2. 每类根因对应的关键模块/文件
3. 每类根因应该看哪些日志或状态
4. 每类根因应该如何验证或排除
5. 哪些根因最值得优先验证

请把不能从代码直接确认的内容标记为“假设”。
```

#### 提示词 3：日志对齐

```text
请先不要改代码。

下面是一次失败执行的数据均衡日志片段：
[粘贴日志]

请按以下格式分析：
1. 按时间线整理关键事件
2. 每个关键事件可能对应的代码模块/函数
3. 当前 balance 任务大概处在哪个状态
4. 失败前最后一个“正常”状态是什么
5. 最可疑的状态切换/异常处理点是什么
6. 我接下来应该重点查看哪些文件和哪些日志关键词
```

#### 提示词 4：日志和代码联动

```text
请根据这段日志，反向定位代码路径。

输出：
1. 最可能打印这些日志的文件/函数
2. 这些函数的上下游调用关系
3. 哪些条件分支可能导致这类失败
4. 我应该继续补充哪几类日志，才能缩小范围
```

#### 提示词 5：先做最小方案再改

```text
请先不要直接改代码。

针对这个 bug：
Nebula Graph 在 storage 服务水平扩容后，执行数据均衡不稳定，经常失败。

请先给我一个最小修复方案：
1. 你认为最可能要改哪些文件
2. 每个文件大概要改什么
3. 哪部分是修复逻辑，哪部分是增强可观测性
4. 风险点是什么
5. 哪些改动必须配套测试

要求：
- 不要大规模重构
- 优先最小改动
- 明确标注假设
- 保持现有风格
```

#### 提示词 6：正式实施最小修复

```text
请根据刚才的分析，实施最小修复。

要求：
- 不做无关重构
- 只改与该 bug 直接相关的文件
- 优先保证状态流转和异常处理正确
- 必要时补充诊断日志，但不要过度打印
- 除非明确不适合，否则补回归测试

交付格式：
1. 修改文件列表
2. 每个文件的改动摘要
3. 修复逻辑说明
4. 新增/修改测试说明
5. 风险点
```

#### 提示词 7：反向审查

```text
请审查这次修复，重点看：
- 是否真的修复了扩容后 balance 失败的根因
- 是否只是掩盖症状
- 是否引入新的竞态/幂等问题
- 是否破坏原有正常路径
- 测试覆盖是否足够
- 是否还缺少更好的可观测性

请按下面格式输出：
- 必须修
- 建议修
- 可选优化
```

#### 提示词 8：发布前检查

```text
请对这次修复做发布前检查：
1. 是否有兼容性风险
2. 是否可能影响其他 balance 场景
3. 是否需要补文档/运维说明
4. 是否需要加开关或保护逻辑
5. 如果修复无效，回滚方案是什么
```

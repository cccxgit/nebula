# Nebula Graph Balance Bug 根因假设树

问题：
Nebula Graph 在 storage 服务水平扩容后，执行数据均衡不稳定，经常失败。

本文档用途：
- 记录根因假设树
- 记录每个假设的验证动作
- 记录验证结果、排除结论和当前判断
- 作为与 Codex 多轮协作时的事实基线

---

## 1. 当前已知事实

> 这里只写已经确认的事实，不写猜测。

- 问题出现在 **storage 服务水平扩容之后**
- 问题与 **data balance / storage balance 执行失败** 有关
- 问题 **可复现**
- 当前具备：
  - 可复现环境
  - 日志定位能力
  - 代码定位能力

---

## 2. 当前未确认但高价值的问题

> 这些问题需要通过日志、代码和实验继续确认。

- 失败是否集中发生在某一类 partition / space / host
- 失败是否与 leader 迁移、节点注册、心跳延迟有关
- 失败是否与特定并发规模、重试次数、超时设置有关
- 失败是否只发生在第一次扩容后的 balance，还是重复发生
- 失败后系统状态是否已经部分变更，导致下一次重试更容易失败
- 失败是“真实执行失败”，还是“状态记录错误导致被判定失败”

---

## 3. 根因假设树

---

### H1. 扩容后元数据视图与实际 storage 状态不同步

#### 假设
扩容后，meta 中感知到的 storage 节点状态、partition 分布或任务视图，与实际 storage 侧状态不一致，导致 balance 任务在执行过程中使用了过期或不完整的信息。

#### 为什么值得怀疑
- 扩容后首先变化的是节点拓扑
- 分布式系统中，元数据一致性与传播延迟常是 balance 类问题的根因
- “经常失败但不稳定”很像视图时序问题

#### 重点查看
- 节点注册、心跳、host 状态更新相关代码
- balance 前获取 host/partition 视图的逻辑
- 任务生成时使用的 cluster view

#### 建议日志关键词
- host status
- heartbeat
- active hosts
- get hosts
- part distribution
- rebuild balance plan

#### 验证动作
- 对比扩容后 meta 记录的 host 状态与 storage 实际状态
- 检查 balance 开始时的节点视图是否稳定
- 比较失败批次与成功批次的 host 视图差异

#### 当前状态
- 状态：待验证
- 优先级：高

---

### H2. Balance 状态机在扩容场景下存在状态流转缺陷

#### 假设
balance task / job / plan 的状态转换在扩容后的某个分支不完整，导致任务在中间状态卡住、重复、跳转错误，或被误判为失败。

#### 为什么值得怀疑
- 这种问题通常表现为“不稳定”
- 分布式任务协调类问题很容易出在状态机边界
- 扩容会引入更多中间状态和异常分支

#### 重点查看
- balance job/task 状态枚举和流转逻辑
- task success / failure / retry / cancel 分支
- 状态持久化与恢复逻辑
- 失败后的状态清理逻辑

#### 建议日志关键词
- task state
- job state
- update status
- transition
- finished / failed / cancelled
- recover task

#### 验证动作
- 梳理一次失败执行的完整状态时间线
- 检查失败前最后一个正常状态
- 对比成功和失败路径的状态差异

#### 当前状态
- 状态：待验证
- 优先级：高

---

### H3. 并发/竞态条件导致 balance 状态被覆盖或判断失真

#### 假设
多个线程、协程或异步回调在更新 balance 任务状态时存在竞态，导致状态覆盖、顺序错乱、重复执行或错误失败判断。

#### 为什么值得怀疑
- “不稳定”“经常失败但非必现”很符合竞态特征
- 扩容后任务量和并发度可能提升
- 分布式调度系统常见问题之一就是异步状态回写顺序问题

#### 重点查看
- 并发执行 task 的调度逻辑
- 状态更新是否加锁、串行化或 CAS
- 异步回调与重试逻辑的关系
- 失败回调和成功回调是否可能交错

#### 建议日志关键词
- concurrent
- callback
- race
- update task status
- duplicated task
- reschedule

#### 验证动作
- 提高日志级别，观察同一 task 是否出现重复回调
- 检查同一状态是否被不同路径重复写入
- 分析失败时是否存在“先成功后失败”或“先失败后成功”的异常顺序

#### 当前状态
- 状态：待验证
- 优先级：高

---

### H4. 迁移过程的超时、重试和错误分类不正确

#### 假设
partition 迁移在扩容场景下更容易出现超时、短暂失败或部分成功，但当前重试策略、超时策略或错误分类不合适，导致可恢复错误被放大成整体失败。

#### 为什么值得怀疑
- balance 本质上是迁移任务
- 扩容后网络、负载、分布会变化
- 常见问题是超时阈值不合理或错误码分类不正确

#### 重点查看
- task timeout 配置和判断
- retry policy
- 错误码到 task 状态的映射
- 部分成功后的处理逻辑

#### 建议日志关键词
- timeout
- retry
- rpc failed
- storage error
- partial success
- backoff

#### 验证动作
- 检查失败样本中 timeout/rpc error 的占比
- 分析重试前后的状态变化
- 验证可重试错误是否被直接标记为失败

#### 当前状态
- 状态：待验证
- 优先级：中高

---

### H5. 新增 storage 节点后的任务分配算法与实际执行状态不一致

#### 假设
balance plan 生成算法在扩容后产生了理论可行、但执行中不稳定的任务分配结果，或生成计划时遗漏了一些实际约束。

#### 为什么值得怀疑
- 扩容直接改变分配输入
- 计划生成问题可能导致后续执行持续不稳定
- 如果失败集中发生在某类迁移目标上，这个方向尤其值得怀疑

#### 重点查看
- balance plan 生成逻辑
- partition 到 host 的重新分配算法
- leader / replica / placement 约束
- plan 与实际执行任务的一致性

#### 建议日志关键词
- generate plan
- balance plan
- target host
- source host
- replica distribution
- invalid target

#### 验证动作
- 对比失败 plan 与成功 plan
- 检查失败任务是否集中在某些 source/target host 组合
- 验证计划生成阶段是否已埋下错误

#### 当前状态
- 状态：待验证
- 优先级：中高

---

### H6. 幂等性缺失，导致失败后重入异常

#### 假设
某些 balance 子任务在第一次失败后已经改动了部分状态，但再次执行时没有正确处理“半完成”场景，导致重试失败或重复失败。

#### 为什么值得怀疑
- “经常失败”有时不是第一次失败，而是失败后的恢复越来越差
- 分布式系统在补偿和重试方面最容易出幂等问题
- 扩容场景更容易暴露半完成状态

#### 重点查看
- task 重试前的清理逻辑
- 已迁移一部分数据时的恢复逻辑
- 重入保护
- 状态检查与跳过逻辑

#### 建议日志关键词
- retry task
- duplicated
- already exists
- partial transferred
- cleanup
- resume

#### 验证动作
- 比较第一次失败和后续重复执行的行为差异
- 检查是否存在“第一次失败后状态更脏”的现象
- 检查重试前是否做了正确清理或跳过

#### 当前状态
- 状态：待验证
- 优先级：中高

---

### H7. Leader 迁移或角色变化与 balance 执行过程耦合

#### 假设
在 balance 执行过程中，leader 变化、raft 状态切换或角色切换与迁移流程产生耦合，导致某些任务在窗口期失败。

#### 为什么值得怀疑
- 分布式存储常见问题
- 扩容和 rebalance 往往伴随 leader 变化
- 这类问题通常表现为“有时成功，有时失败”

#### 重点查看
- leader 相关代码路径
- raft/replica 状态变化日志
- balance 对 leader 状态的依赖逻辑

#### 建议日志关键词
- leader changed
- not leader
- transfer leader
- raft term
- role changed

#### 验证动作
- 检查失败时间点是否存在 leader 变化
- 对比成功/失败批次中的 leader 迁移情况
- 验证 task 是否依赖稳定 leader 条件

#### 当前状态
- 状态：待验证
- 优先级：中

---

### H8. 失败处理逻辑存在误判，真实失败与记录失败不一致

#### 假设
有些任务实际上已经完成或部分完成，但由于结果汇总、状态上报或日志解释问题，被系统误判为失败。

#### 为什么值得怀疑
- “执行不稳定”不一定等于“实际迁移失败”
- 分布式系统里常见“执行成功但控制面判失败”
- 如果数据最终状态与失败记录矛盾，这条非常关键

#### 重点查看
- task result aggregation
- 状态上报和汇总逻辑
- success/failure 判断条件
- 最终一致性检查逻辑

#### 建议日志关键词
- report result
- aggregate result
- mark failed
- final status
- inconsistent result

#### 验证动作
- 对比失败记录与最终数据分布结果
- 检查子任务成功但总任务失败的情形
- 检查结果汇总逻辑的边界条件

#### 当前状态
- 状态：待验证
- 优先级：中

## 4. 验证优先级建议

建议优先顺序：

1. H2 状态机流转问题
2. H1 元数据视图与实际状态不同步
3. H3 并发/竞态导致状态覆盖
4. H4 超时、重试、错误分类问题
5. H6 幂等性与失败后重入问题
6. H5 计划生成算法问题
7. H7 leader 变化耦合
8. H8 失败误判/结果汇总问题
